# 连接排查手册 (`TROUBLESHOOTING.md`)

当你的自定义客户端（或外部工具）**连不上模拟服务器**、**登录后马上断开**或 **收不到图传画面** 时，建议按以下顺序 1 分钟内定位问题。

---

## 第一步：使用自带诊断与探针工具

1. **在模拟服务器本机运行环境诊断**：
   ```bash
   python3 run.py --diagnose
   # 若你的客户端有 terminal.json 配置文件，可顺便一并对比：
   python3 run.py --diagnose --terminal-config /path/to/terminal.json
   ```
   它会检查：本机网卡 IP、相关端口监听状态（`ss -tuln`）、配置主机/端口是否一致，以及本机是否有处于报错状态的活跃终端。

2. **从客户端所在机器向服务端发起主动探测**：
   ```bash
   python3 run.py --probe 127.0.0.1:3333 --probe-id 3 --username <账号> --password <密码>
   ```
   探针会依次检测：**地址解析 → TCP 连通性 → MQTT 3.1.1 CONNECT/CONNACK 登录握手 → SUBSCRIBE 主题订阅与下行首包**。

3. **打开 Web 控制中心审计日志**：
   访问 `http://127.0.0.1:18885/` → 点击 **「登录与客户端」** 页签，查看 **「最近连接与登录审计日志」**，模拟服务器已将对端每次失败的报文特征和修复建议记录在内。

---

## 第二步：10 类常见故障与解决方法

### 1. `ConnectionRefusedError`（TCP 连接被拒绝）
- **常见原因**：
  1. 模拟服务器尚未启动，或端口 `3333` 已被其他进程占用。
  2. 客户端与模拟服务器配置的主机/端口不一致（例如模拟服监听在 `127.0.0.1:3333`，而另一台机器通过局域网 IP 访问）。
- **解决**：
  - 本机联调请确认模拟服已运行且客户端连 `127.0.0.1:3333`。
  - 跨机联调启动模拟服时请传 `--host 0.0.0.0`。

### 2. `Network timeout` / `NetworkUnreachable`（连接超时或网络不可达）
- **常见原因**：
  1. 客户端仍然在连官方赛场硬编码地址 **`192.168.12.1:3333`**，而本机未接入赛场选手端、且未在本机配置 `192.168.12.1` 虚拟地址。
  2. 模拟服务器仅绑定 `127.0.0.1`，但外部主机试图经局域网 IP 连入。
  3. 宿主机防火墙拦截了 `3333/tcp` 或 `3334/udp`。
- **解决**：
  - 本机联调将客户端主机改为 `127.0.0.1`（端口保持 `3333` 即可）。
  - 跨机联调确保服务端以 `--host 0.0.0.0` 启动，并放行防火墙端口（`sudo ufw allow 3333/tcp`）。

### 3. `对端返回了非 MQTT 响应: 'HTTP/1.1 ...'` 或连接后卡死超时
- **常见原因**：把 **Web 控制台端口（`18885`）** 或客户端自己的 API 端口（如 `8090`）误填成了 MQTT Broker 端口。
- **解决**：确认 MQTT 客户端连的是 `--port`（默认 `3333`），浏览器才访问 `--control-port`（默认 `18885`）。反之，如果你用浏览器打开 `http://127.0.0.1:3333/`，模拟服务器会返回 `400 Bad Request` 并在审计日志记录「收到 HTTP 请求而非 MQTT 报文」。

### 4. `CONNACK 0x04` (`BadUserNameOrPassword`)
- **原因**：模拟服务器启动时指定了 `--username`/`--password`、`--user` 或 `--require-auth`，而客户端未填写账密或账密不匹配。
- **解决**：在客户端填入完全一致的账号和密码（注意首尾不能有空格）；如调试阶段不希望鉴权，可在 Web 控制中心「登录与客户端」中把认证模式切回 **开放接入**。

### 5. `CONNACK 0x02` (`IdentifierRejected`)
- **原因**：开启了 `--strict-client-id` 后，客户端使用了非 RM2027 规范的 `Client ID`（例如默认随机字符串 `client-123`）。
- **解决**：按照官方协议要求，将 MQTT `Client ID` 设为机器人编号字符串：红方 `1, 3..9` 或蓝方 `101, 103..109`。

### 6. `CONNACK 0x01` (`UnacceptableProtocolVersion`)
- **原因**：客户端使用了 MQTT 3.1（`MQIsdp` level=3）或 MQTT 5.0（level=5）。
- **解决**：请将客户端库协议版本配置为 **MQTT 3.1.1（protocol level = 4）**。

### 7. `CONNACK 0x03` / `0x05`（服务不可用 / 未授权）
- **原因**：当前机器人在服务端禁用列表中，或 Web 控制台开启了 `fault_connack` 故障注入测试。
- **解决**：检查 Web 控制中心「登录与客户端」中的故障注入下拉框是否选回了「无（正常判定）」。

### 8. 连上几秒后频繁掉线重连（`replaced` 或 `keepalive_timeout`）
- **原因**：
  1. 同时启动了两个使用相同 `Client ID`（例如都是 `"3"`）的客户端进程或探针脚本，触发 MQTT 3.1.1 同 ID 顶替机制。
  2. 客户端开启了高耗时阻塞操作，超过 `1.5 × keep_alive`（最少 15s）未发 `PINGREQ`。
- **解决**：检查审计日志中是否有 `同 Client ID 被新连接顶替下线`，关掉多余的客户端实例或给探测脚本指定不同的 `--probe-id 9`。

### 9. MQTT 已连接但比赛时间不走 / 数据未开始推进
- **原因**：模拟服务器默认以 **待机未开始（`stage=0`）** 启动（图传流会先直接推流，赛程等待开赛指令）。
- **解决**：打开 Web 控制中心 `http://127.0.0.1:18885/` 点击 **「开始完整赛程」** 或 **「直接开始 7 分钟」**，或在启动命令加 `--stage 4`。

### 10. MQTT 正常，但客户端收不到 HEVC 图传画面
- **原因与排查**：
  1. **视频目录为空（`waiting_files`）**：默认从 `./videos` 目录扫描视频文件，若尚未放入 `.mp4`/`.mkv`/`.hevc` 等文件，Web 控制中心「图传媒体库」会提示待放入视频；放入文件后 1.5s 内自动开播。
  2. 模拟服务器启动时加了 `--no-video`，或者触发了 **「规则断流: 超热 / 黄牌 / 红牌」**（可点「解除全部遮挡」或关闭「规则联动断图传」）。
  3. 跨机部署或 Docker NAT 模式下，客户端端口和 IP 不匹配：确认 `--video-host` 指向客户端机器 IP，且模拟服务器和客户端的 UDP 端口一致（默认 `3334`）。
  4. 浏览器解码端要求：WebCodecs `VideoDecoder` 需要浏览器支持 H.265/HEVC 硬解或软解；可通过查看服务端 Web 控制中心的「推流帧与发包统计」与客户端收包计数区分是“UDP 没收到”还是“解码器不支持”。
